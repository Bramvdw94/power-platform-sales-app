# Outlook email and meetings, and Teams notifications, from a code app on plain Dataverse (research for issue #132)

Researched 2026-10-13. Sources are Microsoft Learn and the Microsoft connector reference (cited inline), one practitioner blog where Learn says nothing, and this repo (`power.config.json`, `src/data/dataverse/`). I could not check `dev-salesapp` live: the Dataverse MCP server didn't connect from this sandbox. The checks that need the real environment are listed under [Open points](#open-points).

## Answer

- **Cost: everything recommended here is covered by licences the team already has, with no Azure subscription.** The Office 365 Outlook and Microsoft Teams connectors are **Standard** connectors ([Outlook connector](https://learn.microsoft.com/en-us/connectors/office365/), [Teams connector](https://learn.microsoft.com/en-us/connectors/teams/)). Server-side synchronization is a Dataverse feature that uses the Exchange Online mailboxes the tenant already has. The Microsoft 365 E5 developer sandbox **doesn't include Azure credits**: it includes Exchange Online (Plan 2), Teams and Power Automate for Office 365 (standard connectors only), and it now needs a linked billing account, but it stays free ([developer program FAQ](https://learn.microsoft.com/en-us/office/developer-program/microsoft-365-developer-program-faq)). So credits don't open up any option this note would otherwise reject.
- **Sending email from a record: keep the Office 365 Outlook connector in the code app**, as Send Quote already does (`SendEmailV2` in `generated-client.ts`). Then **have the app write an Email activity** in Dataverse, with Regarding set to the record and status Completed. The app already binds `regardingobjectid_vibe_<table>_<activity>` for Tasks and Phone Calls, so the same bind works for `email`. This costs nothing and needs no per-user setup beyond the Outlook connection each user already makes for Send.
- **Automatic logging of incoming and outgoing email and meetings: use server-side synchronization with Exchange Online on `dev-salesapp`.** No other free option logs mail the user didn't send from the app. Learn only describes it for customer engagement apps, but the Dataverse developer docs describe it as a Dataverse feature, and a practitioner reports it working in a Power Apps-only environment ([Turtledove 2025](https://nati-turtledove.com/2025/01/23/dataverse-activity-tables-exchange-integration/)). **Do a one-mailbox spike before committing** (see Open points).
- **Regarding is the hard part.** Server-side sync **doesn't pick a Lead, Contact, Account or Opportunity as Regarding by itself**. An email gets a Regarding automatically only when it is correlated with an already-tracked email, and then it copies that email's Regarding ([filtering and correlation](https://learn.microsoft.com/en-us/power-platform/admin/email-message-filtering-correlation)). What it does reliably is **resolve the sender and recipients** to Contacts, Accounts, users and other email-enabled tables. So the app should (1) show synced Email and Appointment activities on a Contact, Account or Lead through their **activity parties**, like Related activities, and (2) offer a small "set Regarding" step that proposes the open Opportunity whose Primary Contact is on the email.
- **Optional extra: Dynamics 365 App for Outlook.** It gives salespeople Track and Set Regarding inside Outlook, including for custom tables. It is supported on "model-driven Power Apps that run on Microsoft Dataverse", installed from Marketplace, and needs server-side sync ([deploy App for Outlook](https://learn.microsoft.com/en-us/dynamics365/outlook-app/deploy-dynamics-365-app-for-outlook)). Leave it for later. Our Lead and Opportunity would also have to be set up in its model-driven app.
- **Power Automate per-user flows are the fallback**, not the plan: one flow and one connection per salesperson, Regarding matching written by hand in the flow, and Power Apps Premium covers it only if each flow is linked to the app. **Graph straight from the code app is rejected**: it needs an app registration plus a webhook endpoint for change notifications, and hosting that endpoint means Azure.
- **Teams notification to a user: the Microsoft Teams connector, posting as the Flow bot to a chat with the recipient.** Call it straight from the code app when a user's action triggers the notification (for example Reassign). When the trigger happens on the server (for example an engine Action), use a Dataverse-triggered cloud flow linked to the app. Both use only Standard connectors, plus Dataverse, which Power Apps Premium covers in app context.

## 2. Automatically logging email and meetings

### 2a. Server-side synchronization (recommended)

- **What it is:** "In Power Apps, server-side synchronization provides an interface between Microsoft Dataverse and one or more Exchange servers" ([server-side sync tables](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/server-side-synchronization-entities)). With Exchange it syncs "email, contacts, tasks, and appointments" both ways ([overview](https://learn.microsoft.com/en-us/power-platform/admin/server-side-synchronization)). The admin pages only speak of "customer engagement apps", so plain-environment support isn't stated. The earlier research did find the mailbox and email server profile tables present in `dev-salesapp` ([dataverse-activities](../dataverse-activities.md)), and Turtledove reports it working in "a plain Power Platform-only Dataverse enabled environment".
- **Licence and cost:** it needs Exchange Online in the same tenant ([connect to Exchange Online](https://learn.microsoft.com/en-us/power-platform/admin/connect-exchange-online)). The developer tenant has Exchange Online Plan 2. No Microsoft page I found names a licence for server-side sync itself. Turtledove notes Microsoft Support told him D365 apps were needed, and his own test disagreed. **Treat it as included with Power Apps Premium plus Exchange, and confirm with the spike.**
- **One-time setup (admin):** check the default "Microsoft Exchange Online" server profile, set Process Email Using to Server-Side Synchronization, then approve and Test & Enable each mailbox ([connect to Exchange Online](https://learn.microsoft.com/en-us/power-platform/admin/connect-exchange-online)). Approving needs System Administrator **plus** Global or Exchange admin, which Bram is on the developer tenant. Alternatively, turn off "Process emails only for approved users".
- **Per user:** an enabled mailbox, plus a personal tracking choice. Use **"Email messages from records that are email enabled"**: "Messages from any record that resolves to an email address … including custom tables, are tracked." The other choices are "All email messages", "in response to email", "from Leads, Contacts, and Accounts" and "No email messages" ([filtering and correlation](https://learn.microsoft.com/en-us/power-platform/admin/email-message-filtering-correlation)). "Leads" there means the standard `lead` table, which `dev-salesapp` doesn't have. Our Lead counts only if **Sending email** (email-enabled) is turned on for `vibe_lead`, a switch that can't be undone ([edit tables](https://learn.microsoft.com/en-us/power-apps/maker/data-platform/edit-entities)).
- **Meetings:** appointments created in Dataverse sync to Outlook. Meetings made in Outlook are logged when the user gives them the **"Tracked to Dynamics 365" category**. That works for "an email, appointment, or task", syncs within about 15 minutes, and covers every occurrence of a recurring meeting ([category tracking](https://learn.microsoft.com/en-us/power-platform/admin/use-outlook-category-track-appointments-emails)). The same category also lets a user log a single email by hand.
- **How Regarding is matched:**
  - Correlation with an already-tracked email (tracking token, then email headers, then smart matching) copies that email's Regarding. Folder-level tracking and tracking tokens are the accurate methods ([Email tab settings](https://learn.microsoft.com/en-us/power-platform/admin/system-settings-dialog-box-email-tab), [filtering and correlation](https://learn.microsoft.com/en-us/power-platform/admin/email-message-filtering-correlation)).
  - A brand-new incoming email gets **no Regarding**. Its From/To/Cc are resolved to Contacts, Accounts, users or email-enabled custom rows. If more than one row matches, all of them are linked unless "Set To, cc, bcc fields as unresolved values if multiple matches are found" is on.
  - So the app needs: email and appointment rows on a Contact, Account or Lead's timeline by **party** (the Related-activity pattern, extended to parties), and a "set Regarding" action that suggests the open Opportunity where the party is the Primary Contact.
- **Limits:**
  - "An Exchange mailbox (email address) can only synchronize appointments, contacts, and tasks with one organization" ([deploy App for Outlook](https://learn.microsoft.com/en-us/dynamics365/outlook-app/deploy-dynamics-365-app-for-outlook)). Each salesperson's mailbox can sync with `dev-salesapp` **or** a later production environment, not both.
  - It is asynchronous: category-tracked items take up to about 15 minutes.
  - Email from distribution groups, aliases or Bcc "might not be reliably categorized" ([category tracking](https://learn.microsoft.com/en-us/power-platform/admin/use-outlook-category-track-appointments-emails)).
  - Synced emails use the standard `email`, `appointment` and `activityparty` tables, which are polymorphic. **Reading** them from the code app works. **Writing** parties is unproven (section 1, option B).

### 2b. Dynamics 365 App for Outlook (optional, later)

An Outlook add-in that shows the matching Contact or Account and lets the user Track an email or meeting and **Set Regarding** to any activity-enabled table, custom ones included ([customize App for Outlook](https://learn.microsoft.com/en-us/power-apps/maker/model-driven-apps/app-for-outlook-customize)). It needs server-side sync and the "Dynamics 365 App for Outlook User" role, and it installs from Marketplace into a Dataverse environment ([deploy](https://learn.microsoft.com/en-us/dynamics365/outlook-app/deploy-dynamics-365-app-for-outlook)). Turtledove reports it running in a Power Apps-only environment and covered by Power Apps Premium. It is a model-driven app inside Outlook, so it is a second UI next to the code app. It is the best way to get Regarding set at the moment of tracking, so add it if the in-app "set Regarding" step proves too much work.

### 2c. Power Automate flows (fallback)

- **How:** an automated flow per salesperson, triggered by "When a new email arrives (V3)" and "When an event is added, updated or deleted (V3)" on their mailbox ([Outlook connector](https://learn.microsoft.com/en-us/connectors/office365/)). The flow looks up the Contact by address and creates the `email` or `appointment` row with Regarding. Sent mail needs a second trigger on Sent Items, because a trigger checks only the folder it is set to.
- **Licence:** "Automated and scheduled flows always run in the context of the flow owner." Because the flow writes to Dataverse (a premium connector), it is covered by Power Apps Premium only if it is **linked to the app** ("associated to an app through PowerShell or the Power Automate portal"). Otherwise the owner needs Power Automate Premium ([Power Automate licensing FAQ](https://learn.microsoft.com/en-us/power-platform/admin/power-automate-licensing/faqs)).
- **Per-user setup:** one flow owned by each user with their own Outlook connection. The connection can't be shared, and Office 365 "does not support Service Principal-based authentication" ([Outlook connector](https://learn.microsoft.com/en-us/connectors/office365/)).
- **Regarding:** whatever the flow's own matching logic decides.
- **Limits:** we would rebuild what server-side sync already does (dedup, threads, attachments), flows count against Power Platform request limits, and someone has to keep a flow per user alive. Use it only if the spike shows server-side sync won't run on `dev-salesapp`.

### 2d. Microsoft Graph from the code app (rejected)

The Outlook connector's "Send an HTTP request" already reaches Graph `/me/messages`, `/me/events` and `/me/calendar` through the user's connection ([Outlook connector](https://learn.microsoft.com/en-us/connectors/office365/)). It can read mail on demand while the app is open, but it can't log in the background. Background logging with Graph needs change notifications, which post to a public HTTPS endpoint we would have to host. That means Azure or a premium HTTP-trigger flow, so it breaks the cost rule and duplicates server-side sync.

## 3. Teams notification to a user

| Option | How | Cost | Setup | Limits |
|---|---|---|---|---|
| **Teams connector from the code app (for user-triggered events)** | `TeamsService.PostMessageToConversation` with "Post as: Flow bot", "Post in: Chat with Flow bot", recipient UPN, HTML body (code-apps add-teams skill). Example: notify the new Owner on Reassign | Standard connector ([Teams connector](https://learn.microsoft.com/en-us/connectors/teams/)) | Add the `teams` data source. Each user makes a Teams connection once. The Workflows app must be allowed in the Teams admin center | ~28 KB per message. 25 Flow-bot calls per 300 s per connection. Flow bot only in commercial tenants. Not to private channels |
| **Dataverse-triggered cloud flow (for server-side events)** | "When a row is added, modified or deleted" on, say, `vibe_quote` or Task, then Teams "Post message" as Flow bot to the Owner | Dataverse is premium, so the flow must be **linked to the code app** and its owner must have Power Apps Premium ([licensing FAQ](https://learn.microsoft.com/en-us/power-platform/admin/power-automate-licensing/faqs)) | One flow in the solution, owned by a service user or admin with a Premium licence | Same Teams limits. Runs asynchronously, a few seconds after the save |

Teams "Post a feed notification" (activity feed) is in the same 25-per-300 s bucket. It needs a Teams app, so a chat message is simpler.

## Open points

1. **Spike server-side sync on `dev-salesapp` with one mailbox:** check the default Exchange Online profile exists, approve and enable Bram's mailbox, send a mail from a Contact's address, and confirm an `email` row appears with resolved parties. If it fails with an "enable D365 apps" style error, switch to 2c.
2. **Licence wording for server-side sync** on a Power Apps-only environment isn't stated on any Microsoft page I found. Confirm it before going beyond the developer tenant.
3. **Code-app spikes:** create an `email` row with a Regarding bind (expected to work, like Task), write the activity-party collection, and call the bound `SendEmail` action. These decide between options A and B in section 1.
4. **Turn on "Sending email" for `vibe_lead`?** It is needed for Lead emails to auto-track and resolve, and it can't be turned off. Opportunity doesn't need it.
5. **One mailbox, one environment:** when a production environment arrives, mailboxes move there and `dev-salesapp` stops syncing them.
6. **Glossary:** Activity currently means Note, Task or Phone Call. v3 adds Email and Appointment (or "Meeting"), plus a term for an activity without a Regarding that is waiting to be linked. Pin the names before building.
7. **Teams admin:** check that the Workflows app is allowed in the Teams admin center of the developer tenant.
